## 1. システム概要

### 1.1 目的

現行のかりポムは、Mac（KariPom Companion／macOSはScreenCaptureKit使用）+ Python + UDP により音量・FFT情報をCoreS3へ送信し、口パク・グライコフェイスを実現している。本設計は、この「Mac依存の耳」を、**CoreS3を一切分解せず、Port C（Grove）1本だけで接続できる独立音声解析ユニット「Karipom Ear v2」**へ置き換えるためのアーキテクチャを定義する。

### 1.2 設計思想（3原則）

1. **役割分離** — Ear（Pico側）が「聴く・解析する」、CoreS3が「表現する」。CoreS3ではFFT等の重いDSPを一切行わない。
2. **CoreS3非侵襲** — 筐体を開けない。M-BUS配線をしない。接続はPort C（G17/G18・UART）のみ。CoreS3側ソフト変更も最小限（受信パーサ追加のみ）。
3. **Ear側だけで進化** — 通信プロトコルをバージョン付きで固定し、Pico側ファーム更新だけで Ver1→Ver2→Ver3 と性能向上できる構造にする。

### 1.3 重要な設計判断（要旨）

| 論点 | 結論 | 一言理由 |
|---|---|---|
| 実現可能性 | **実現可能（高確度）** | Port C空き・3.3Vロジック整合・帯域余裕を実機コードで確認済 |
| 通信方式 | **UART（Port C標準機能）** | Port CはCoreS3のUART専用Grove。SPIは物理的に不可、I2Cは劣位 |
| マイコン | **Raspberry Pi Pico 2 H（RP2350）** | FPU+DSP命令でFFT/VADが余裕。依頼書の3候補より明確に優位 |
| ADC | PCM1808基板（ライン入力）**+ I2S MEMSマイク併設を強く推奨** | ⚠ PCM1808はライン入力専用でマイクを直接接続できない（§2.4） |
| プロトコル | 互換テキスト（Phase 0）→ バイナリv1+CRC8（Phase 1） | 既存UDP書式と同義のデータでCoreS3変更を最小化 |

## 2. 実現可能性評価

### 2.1 結論

**構成は実現可能。** ただし無条件ではなく、以下の4点を評価した。◎=問題なし、○=対策込みで可、⚠=構想の欠落（対策を§2.4で提案）。

| # | 評価項目 | 判定 | 根拠 |
|---|---|---|---|
| 1 | Port C接続性 | ◎ | CoreS3のPort C（G17=TXD/G18=RXD）は現行コードで完全未使用。UARTはESP32-S3のハードウェア機能でCPU負荷ほぼゼロ |
| 2 | 電気的整合 | ◎ | CoreS3・Pico・PCM1808すべて3.3Vロジック。Grove 5VからPico(VSYS)とPCM1808基板(DC5V可)へ給電可能 |
| 3 | 通信帯域 | ◎ | 特徴量50Hz送信でも約10kbps。UART 115200bpsの1割未満 |
| 4 | Pico側I2S受信+DSP | ○ | arduino-pico 5.6.1標準の`setSlave()`スレーブ入力で受信（§6.3）。FFT/VAD/RMSはRP2350なら大幅な余裕 |
| 5 | 音の入口 | ⚠ | **PCM1808はライン入力（3.5mm）専用。マイクを繋げない。**「部屋で流れる音楽に反応」「外部音声入力」にはマイクが別途必要（§2.4） |
| 6 | 電源容量 | ○ | Ear全体で実測想定60〜100mA。Grove 5Vで供給可能だが、既存サーボ2軸と5Vバスを共有するため実測確認を推奨（§13-3） |

### 2.2 帯域・レイテンシ試算

- 特徴量フレーム：20バイト（同期2+ヘッダ3+ペイロード14+CRC1）× 50Hz = 1,000 B/s、UART実効（10bit/byte）≒ **10kbps**（115200bpsの約9%）
- 口パク遅延バジェット：音声ブロック取得16ms（256サンプル@16kHz）+ DSP約2ms + UARTフレーム約1.7ms + CoreS3描画1フレーム ≒ **合計40ms未満**。人間が違和感を覚える約100msに対して十分な余裕。現行Mac→UDP経路（KariPom Companion+Python+Wi-Fi）より短縮が見込める。

### 2.3 現行コードとの適合性（確認済み事実）

添付コード stable_2.2 を精査した結果、Ear v2にとって好都合な土台が既に存在する：

- `FFT:25,13,0,0,0,0,0,0`（8バンド・0〜100・約12.5Hz）を受けて表示する **Visualizer Face** が実装済み
- `SPEAK_START` / `SPEAK_STOP` + ハートビート + タイムアウト監視（`SPEAK_TIMEOUT_MS`、`FFT_RX_TIMEOUT_MS=400ms`）という **受信途絶に強い状態機械** が実装済み
- つまりCoreS3側は「同じ意味のデータがUARTからも入ってくる」ようにするだけでよい。**表示・口パク・watchdogのロジックは1行も変えずに済む**（§10）

### 2.4 構想の唯一の欠落：マイク入力

PCM1808はライン レベル（約1Vrms）専用ADCであり、マイク（数mVrms）を直接接続しても実用感度が得られない。将来目標の「音楽でダンス」「外部音声入力」「AI音声解析」は**空気中の音を聴く**ことが前提のため、以下を提案する：

- **推奨：I2S MEMSマイク（INMP441等、約300〜500円）をPicoに併設**。PicoのPIOは複数系統のI2Sを同時に扱えるため、**ライン入力（PCM1808）とマイクの2系統を持つ「両耳」構成**が追加コストほぼゼロで成立する。
- 代替：マイクアンプ基板（MAX9814等）の出力をPCM1808のLINE INへ入れる方法もあるが、部品点数・ノイズ・ゲイン調整の面でMEMSマイク直結に劣る。

この提案を反映した最終推奨構成を§14に示す。PCM1808が無駄になるわけではない——Mac/スマホ/DAPのイヤホン出力を3.5mmで直結すれば、**現行のPC経由（Wi-Fi）経路より高品質な有線口パク・ダンス連動**が実現する。

## 3. 採用理由

### 3.1 通信方式：UART採用（比較評価）

Port Cの物理制約：Grove 4ピン（5V / GND / G17 / G18）。**信号線は2本のみ。**

| 評価軸 | UART | I2C | SPI |
|---|---|---|---|
| Port Cで物理的に成立するか | ◎ Port CはCoreS3の**UART専用設計ポート**（G17/G18） | ○ 2線で成立 | × 最低4線（SCK/MOSI/MISO/CS）必要。**不成立** |
| 通信の主導権 | ◎ 全二重・双方向。Picoが自発的に送れる（プッシュ型） | △ CoreS3がマスタとしてポーリング必須。loop()の負荷・タイミング依存が増える | — |
| スレーブ実装の安定性 | ◎ 双方ハードUARTで枯れている | △ RP2040/RP2350のI2Cスレーブは制約が多く（クロックストレッチ問題等）、trouble事例が多い | — |
| ケーブル耐性（30cm級Grove線） | ◎ 低速非同期で最も堅牢 | △ プルアップ・容量の影響を受けやすい | — |
| デバッグ容易性 | ◎ USBシリアルでそのまま覗ける。テキストモード併用可 | △ 専用ツールが要る | — |
| 既存設計との親和性 | ◎ 既存UDPテキスト書式をそのまま流せる | △ レジスタマップ設計が別途必要 | — |

**結論：UART一択。** 速度も115200bpsで要件の10倍以上、必要なら921600bpsまで引き上げ可能（プロトコルは速度非依存に設計、§8）。

### 3.2 マイコン：Pico 2 H 採用（比較評価）

依頼書の3候補＋現行世代を含めて比較する。

| 項目 | Pico | Pico H | Pico Zero (Waveshare RP2040-Zero) | **Pico 2 H（推奨）** |
|---|---|---|---|---|
| SoC | RP2040 | RP2040 | RP2040 | **RP2350** |
| CPU | Cortex-M0+ ×2 @133MHz | 同左 | 同左 | **Cortex-M33 ×2 @150MHz** |
| FPU / DSP命令 | なし / なし | なし | なし | **あり / あり（SIMD MAC）** |
| SRAM | 264KB | 264KB | 264KB | **520KB** |
| FFT・VADの実装 | 固定小数点で要最適化 | 同左 | 同左 | **float直書きで余裕（実測系比較で約2倍、浮動小数点は桁違い）** |
| ヘッダ / デバッグ | 自分ではんだ付け / SWDスルーホール | ヘッダ済 / 3ピンJSTデバッグ | はんだ済(一部) / SWDパッドのみ | **ヘッダ済 / 3ピンJSTデバッグ** |
| 供給元 | 公式 | 公式 | サードパーティ（Waveshare） | **公式** |
| 国内実売目安 | 約700〜800円 | 約900〜1,000円 | 約900円前後 | **約1,000〜1,300円**（秋月・スイッチサイエンス取扱あり） |
| 数年スパンの入手性 | 公式で長期供給 | 同左 | メーカー依存 | **公式・現行世代で最良** |

**採用理由（Pico 2 H）：**

1. **DSP適性が別次元** — RP2350はFPUとDSP拡張命令を持ち、FFT・フィルタ・VAD・将来のビート追跡やMLワードスポッティングまでfloatで素直に書ける。RP2040では固定小数点化・アセンブラ最適化という保守性の敵を抱え込む。「Pico側だけ更新で Ver1→Ver3」という要求に対し、**計算余力＝将来性**である。
2. **Hの価値** — ヘッダ実装済みで基板化が容易、かつ3ピンJSTデバッグコネクタでSWDデバッグ可能。長期保守に効く。
3. **差額は数百円** — 本体価格差300〜500円で上記を得られる。迷う余地がない。
4. RP2040との**ピン互換・ツール互換**（Arduino-Pico / Pico SDK共通）のため、依頼書前提のRP2040系知見はすべて流用可能。手元にPico/Pico Hが既にあるなら**Phase 0（PoC）はそれで開始し、Phase 2以降でPico 2 Hに載せ替える**運用も成立する（同一ソース・同一配線）。

Pico Zeroは小型さが魅力だが、非公式・SWD引き出し困難・露出ピン数減のため、長期保守目的の本件では非推奨。なお無線版（Pico 2 W）は将来のOTA更新用オプションとして§12で触れる。

### 3.3 アーキテクチャ：分離型を採用（ゼロベース検討の結果）

ゼロベースで3案を比較した。

| 案 | 構成 | 評価 |
|---|---|---|
| A. CoreS3単体 | 内蔵デュアルマイク（ES7210）+ ESP-DSPでCoreS3が自前解析 | × ハード追加ゼロは魅力だが、(1)表情描画・サーボ・Webサーバ・カメラと同一CPUでDSPが競合し、安定性最優先の現方針と真っ向から矛盾 (2)自機スピーカー音の回り込み (3)ライン入力不可 (4)「CoreS3は表現専任」という本依頼の思想に反する |
| B. Grove接続マイクユニットをPort C直結 | PDM/アナログマイクユニット | × 結局DSPをCoreS3が担うことになり案Aと同じ欠点。Port Cを低レベル信号に占有し拡張性も失う |
| **C. 分離型（採用）** | **Pico 2 + PCM1808 + MEMSマイク、UARTで特徴量のみ送る** | ◎ CoreS3は表現専任のまま。Ear側は独立して開発・テスト・進化可能。故障時も切り離せる（Earを抜いてもかりポムは現状機能で完全動作） |

案Cの隠れた利点：**Earは単体でUSB接続してMacでも開発・検証できる**。かりポム本体を占有せずに音声解析だけを改良できるため、開発サイクルが速い。

### 5.2 電源系統

```
CoreS3 Port C 5Vピン ──┬── Pico 2 H VSYS（ピン39）※内部ダイオード経由で安全
                       └── PCM1808基板 VDD（DC5V〜12V入力対応）
CoreS3 Port C GNDピン ──── 共通GND（Pico GND・PCM1808 GND・マイクGND）
INMP441 VDD ◄── Pico 3V3 OUT（ピン36）
```

- 消費電流（想定）：Pico 2 約30〜50mA + PCM1808基板 約20〜30mA + INMP441 約2mA = **最大約80mA**
- Grove 5VはCoreS3内部電源（AXP2101系）から供給され、サーボ2軸と共有。Ear追加分80mAは軽微だが、**サーボ動作時ピークとの合算を初回に実測すること**（§13-3）
- PicoのVSYS給電は内蔵ダイオード経由のため、**USB（開発PC）とGrove 5Vが同時接続されても衝突しない**（Pico設計仕様）。ただし作法として書き込み時はGroveを抜く運用を推奨

### 5.3 実装形態

- Ear一式（Pico 2 H + PCM1808 + マイク）を1枚の小基板にまとめ、かりポム頭部側面の「耳」位置に3Dプリント筐体で装着することを推奨（マイクは筐体外向きに開口、スピーカーからの回り込み低減のため本体スピーカーと反対面が理想）
- CoreS3本体には**Groveケーブル1本が刺さるだけ**。分解・改造は一切なし（最優先条件充足）

### 6.3 I2Sクロック方式（v1.3確定：単一方式）

**方式は1つだけ：PCM1808基板＝マスタ、Pico＝スレーブ受信（arduino-pico 5.6.1標準の`setSlave()`）。** 基板搭載の24.576MHz発振器がSCKI/BCLK/LRCKを生成し、Picoは3線を入力として受けるのみ。Picoがクロックを出力する構成（旧・戦略B）は、PCM1808のスレーブ時LRCK-SCKI同期要件（±6BCK超でADC停止・ゼロ出力）と基板発振器の常時駆動により**原理的に不成立のため廃止済み**（監査記録は実装仕様書v2.0 §0）。

| 項目 | 確定内容 |
|---|---|
| 基板ジャンパ | 出荷状態 M-96K（全OPEN）で予備試験 → 正式運用は **M-48K（OP2=SHORT/OP3=OPEN）**。SLAVE設定は使用禁止 |
| Pico側API | `I2S(INPUT)` → `setSlave()` → `setDATA(2)` → `setBitsPerSample(32)` → `begin(fs)`。`setBCLK()`/`setMCLK()`は使用しない |
| クロック期待値 | M-96K：BCLK 6.144MHz／LRCK 96.000kHz ・ M-48K：BCLK 3.072MHz／LRCK 48.000kHz（MCLKピンは常時24.576MHz出力＝未接続のまま） |
| フォールバック | M-96K⇔M-48Kの切替のみ。それでも不可なら基板不良を疑う（最終手段はINMP441前倒し） |

FORMATジャンパは **I2S-24（OP1=OPEN、基板デフォルト）** とする（v1.1修正：本基板のFORMATジャンパはOP1）。

サンプルレートは48kHzで受信し、Pico内部で16kHzへデシメーション（1/3間引き+LPF）して解析する。口パク・ダンス・VADに必要な帯域は8kHz以下であり、FFT演算量を1/3にできる。

## 8. 通信プロトコル設計

### 8.1 二層構造：互換テキストモード＋バイナリモード

**Phase 0（互換テキストモード）** — Earは既存UDPプロトコルと同一の行指向テキストをUARTへ送る：

```
FFT:25,13,0,0,0,0,0,0\n      （8バンド 0〜100、25Hz）
SPEAK_START\n                 （VAD発話開始＋1秒毎ハートビート）
SPEAK_STOP\n                  （発話終了）
```

CoreS3側は既存パーサをUART入力に対してもほぼそのまま呼ぶだけで動作する。**最小の追加コードで即日結線テストが可能**であり、これが「CoreS3側は可能な限り変更不要」の最短経路である。

**Phase 1以降（バイナリモード v1）** — 長期運用の正式プロトコル。CRCによる破損検出、バージョン番号による前方互換、拡張フィールドを持つ。

### 8.2 バイナリフレーム構造

```
┌──────┬──────┬─────┬──────┬─────┬─────────────┬──────┐
│ 0xA5 │ 0x5A │ VER │ TYPE │ LEN │ PAYLOAD     │ CRC8 │
│ 同期1 │ 同期2 │ 1B  │ 1B   │ 1B  │ 0〜32B      │ 1B   │
└──────┴──────┴─────┴──────┴─────┴─────────────┴──────┘
CRC8: Dallas/Maxim（多項式0x31）、VER〜PAYLOAD末尾を対象
```

受信側規則（前方互換の要）：
1. 未知のTYPEは**黙って読み捨てる**（エラーにしない）
2. LENが期待より長い場合、既知部分だけ解釈し残りを無視する（**フィールド追加でCoreS3を壊さない**）
3. CRC不一致は当該フレームのみ破棄（再送要求はしない。次フレームが50ms後に来る）
4. VERメジャー不一致時のみ互換テキストモードへフォールバック

### 8.3 フレーム種別

**TYPE 0x01: FEATURE（Ear→CoreS3、25Hz標準・50Hzまで設定可）** — ペイロード14バイト

| オフセット | 型 | 名称 | 内容 |
|---|---|---|---|
| 0 | u8 | seq | 循環シーケンス番号（欠落検出） |
| 1 | u8 | flags | bit0:VAD発話中 bit1:onset bit2:beat bit3:clip bit4-5:音源(0=LINE,1=MIC,2=MIX) |
| 2 | u8 | rms | 音量RMS 0〜100 |
| 3 | u8 | peak | ピーク 0〜100 |
| 4〜11 | u8×8 | band[8] | 8バンドFFT 0〜100（低音→高音、既存Visualizer Faceと同スケール） |
| 12 | u8 | tempo | 推定BPM/2（0=未検出）※Ver2以降で有効値 |
| 13 | u8 | reserved | 0固定（将来拡張） |

**TYPE 0x02: EVENT（Ear→CoreS3、発生時のみ）** — SPEAK_START(1) / SPEAK_STOP(2) / ONSET(3) / BEAT(4) / CLIP(5) / SILENCE_ENTER(6)

**TYPE 0x03: STATUS（Ear→CoreS3、1Hz）** — FWバージョン、fs、動作モード、ノイズフロア、CPU負荷、稼働秒、エラー累計。CoreS3のWeb Cockpitにそのまま表示するための自己申告フレーム。

**TYPE 0x10: CMD（CoreS3→Ear）** — SET_MODE(音源選択) / SET_RATE(12.5/25/50Hz) / SET_GAIN / SET_TEXTMODE / PING / RESET。ACKはSTATUSで代替（コマンド応答用の複雑な状態を持たない）。

### 8.4 意味論の既存互換

| 既存UDP（Mac経路） | Ear v2バイナリ | CoreS3内部での扱い |
|---|---|---|
| `FFT:a,b,...` 12.5Hz | FEATURE.band[8] | `fftLevel[8]`へ格納、`lastFftPacketTime`更新（完全同義） |
| `SPEAK_START`+HB | EVENT SPEAK_START + FEATURE.flags.VAD | `externalSpeaking=true`、`lastSpeakPacketTime`更新 |
| `SPEAK_STOP` | EVENT SPEAK_STOP | `externalSpeaking=false`、口閉じ |
| （なし） | rms/peak/beat/tempo | 新規状態変数（将来のダンス同期用、当面は保持のみ） |

## 9. Pico ソフトウェア構成

### 9.1 開発環境

- **Arduino IDE + arduino-pico（earlephilhower版）コア** を推奨。理由：(1)かりポム本体と同じArduino環境で保守知識を共有 (2)RP2040/RP2350両対応で載せ替え自由 (3)PIOベースI2Sライブラリ（スレーブ入力`setSlave()`対応）を同梱
- 書き込みはUSB UF2ドラッグ&ドロップ（BOOTSELボタン）。**CoreS3側の書き込み環境と完全独立**

### 9.2 モジュール構成

```
┌─ Core 0（信号処理専任）──────────────────────────┐
│ audio_in    : PIO+DMA I2S受信（ダブルバッファ256サンプル）│
│ decimator   : 48kHz→16kHz（LPF+1/3間引き）              │
│ dsp_core    : DCカット → Hann窓 → FFT512 → 8バンドlog集約 │
│             → RMS/Peak → AGC・ノイズフロア追跡（最小統計法）│
│ vad         : エネルギー+スペクトル判定、アタック2フレーム/  │
│               リリースハングオーバ400ms                    │
│ beat        : スペクトラルフラックスonset検出（Ver2でBPM追跡）│
└──────────────── リングバッファ（特徴量）───────────────┘
┌─ Core 1（通信・管理専任）─────────────────────────┐
│ protocol    : フレーム組立・CRC8・送信スケジューラ（25Hz）   │
│ cmd_handler : CoreS3からのCMD処理・NVS相当の設定保存(flash) │
│ status      : 1Hz STATUS送信・LED状態表示                  │
│ usb_debug   : USBシリアルへ人間可読ログ（UARTとは独立）      │
└─────────────────────────────────────────────────┘
```

2コア分担により、**通信やログがどれだけ増えても信号処理のリアルタイム性が壊れない**。これはかりポム本体で経験済みの「ログ汚染との戦い」をアーキテクチャで予防するもの。

### 9.3 処理負荷見積（RP2350）

FFT512点（float・radix-2）は数十万サイクル程度＝150MHzで約2〜3ms、フレーム周期40ms（25Hz）に対し**CPU使用率10%未満**。RP2040でも固定小数点化すれば成立するが、余力の差が将来機能（§12）の上限を決める。

### 9.4 バージョニング

- Ear FWは semver（EAR_FW 2.0.0 から開始）。STATUSフレームで常時自己申告し、CoreS3のCockpitと起動ログに表示
- **プロトコルVERとFWバージョンを分離**する（FWがVer3になってもプロトコルv1のままならCoreS3は無変更）

## 10. CoreS3 ソフトウェア構成

### 10.1 変更方針：追加のみ・既存関数無改変

stable_2.2 の安定性を守るため、**既存関数の内部には触れない**。追加は以下の4点のみ（合計150行程度の見込み）：

1. `setup()`：`Serial2.begin(115200, SERIAL_8N1, 18, 17);` を1行追加
2. `loop()`：`handleEarUart();` を1行追加（`handleUDP()`と並置）
3. 新規関数 `handleEarUart()`：フレームパーサ。**handleUDP()と同じ状態変数**（`fftLevel[]`、`externalSpeaking`、`lastFftPacketTime`、`lastSpeakPacketTime`）に書き込むだけ。表示・口パク・watchdog・スリープ連動は既存ロジックがそのまま反応する
4. Web Cockpit：EARステータス行（LINK/FW版数/VAD/音源）を1ブロック追加

### 10.2 AudioFeatureHub（概念モデル）

```
 UDP(Mac経路)──┐
               ├──► 共有状態変数群（fftLevel[] / externalSpeaking / rms ...）──► 表現層（無変更）
 UART(Ear v2)──┘         ▲
                    ソース調停（§10.3）
```

物理的に新しいクラスを作る必要はない。「**2つの入口が同じ変数に書く**」という現行コードの延長で実現し、既存のタイムアウト監視がそのまま両ソースの切断検出を担う。

### 10.3 ソース調停ルール

| 状況 | 動作 |
|---|---|
| Ear接続・受信中 | **Ear優先**。UDPのFFT/SPEAKは無視（TIME_SYNCは例外的に受理継続） |
| Ear途絶400ms超 | 自動的にUDP（Mac経路）へフォールバック。ログ1行記録 |
| 両方途絶 | 既存動作（口閉じ・Visualizer減衰）——現行watchdogのまま |

この設計により、**Ear v2を接続してもMac経路は「保険」として一切壊れない**。移行期・デバッグ期の安全網になる。

### 10.4 ログ方針

既存の「FFTパケットはログ抑止」ポリシーをUART側にも同一適用（FEATUREフレームはログしない。EVENT・STATUS・エラーのみ記録）。SDログ肥大化対策（logtoilet）の思想を踏襲する。

## 11. データ構造設計

### 11.1 Pico側（送信）／CoreS3側（受信）共通構造体

```c
// プロトコルv1 FEATURE ペイロード（14バイト・packed）
typedef struct __attribute__((packed)) {
  uint8_t seq;        // 循環シーケンス
  uint8_t flags;      // bit0:VAD bit1:onset bit2:beat bit3:clip bit4-5:src
  uint8_t rms;        // 0-100
  uint8_t peak;       // 0-100
  uint8_t band[8];    // 0-100 ×8バンド（低音→高音）
  uint8_t tempo;      // BPM/2, 0=unknown
  uint8_t reserved;   // 0固定
} EarFeatureV1;

// CoreS3側 受信状態（既存変数への写像＋新規保持分）
typedef struct {
  bool     linkUp;          // STATUS受信で更新、3秒途絶でfalse
  uint8_t  fwMajor, fwMinor;
  uint8_t  source;          // 0=LINE 1=MIC 2=MIX
  uint8_t  rms, peak, tempo;
  uint32_t rxFrames, crcErrors, seqGaps;  // Cockpit診断用
} EarLinkState;
```

### 11.2 互換性ルール（再掲・規範）

1. 既存フィールドの**位置・型・意味は永久不変**（変更したくなったら新TYPEを追加する）
2. 拡張は「末尾追加+LEN増加」または「新TYPE」でのみ行う
3. `reserved`・未知TYPE・超過LENの黙殺を受信側必須要件とする
4. スケール（0〜100）・バンド数（8）・バンド割りは既存Visualizer Faceと同一に固定。変更が必要になった場合は新TYPE（例：0x04 FEATURE16）を追加し、旧TYPEも並行送信可能とする

このルールが「**Pico側のみ更新で Ver1→Ver2→Ver3**」の契約書である。

## 付録A：参考情報

- RP2350（Pico 2）はCortex-M33×2・FPU・DSP拡張命令搭載で、RP2040比で音声DSP系処理が大幅に高速（浮動小数点はハードウェア実行）
- Pico 2 H は秋月電子・スイッチサイエンスで国内流通中
- arduino-pico 5.6.1はI2Sスレーブ入力（`setSlave()`）を標準搭載。ピン規則はDIN,DIN+1,DIN+2の3連番固定・`setBCLK()`無視（5.6.1同梱pio_i2s.pio.hのコメントで明記）。Phase 0 Step 1での実機検証を前提とする
- PCM1808基板ジャンパ（v1.1・実機裏面シルク準拠）：M/S＝OP2/OP3（M-96K=OPEN/OPEN、M-48K=SHORT/OPEN、SLAVE=SHORT/SHORT【使用禁止】）、FORMAT＝OP1（I2S-24=OPEN）。OP4・M-64Kは本基板に存在しない

## 付録B：組立チェックリスト（Phase 0）

1. PCM1808ジャンパ：予備試験は全OPEN（M-96K）のまま。正式移行時のみ OP2=SHORT（M-48K）。OP1=OPEN（I2S-24）・OP3=OPEN。SLAVE設定は使用禁止
2. I2S配線順：DATA→GP2／BCLK→GP3／LRCK→GP4（3連番固定）。MCLKは未接続
3. Grove線色とG17/G18の対応をテスターで確認（クロス接続：Pico TX→CoreS3 RX）
4. 電源投入順は任意（プロトコルはステートレス）
5. PicoのUSBシリアルでFFT値を目視確認 → その後CoreS3接続
6. CoreS3 Cockpitで受信状態確認、サーボ同時動作時の5V電圧を実測
