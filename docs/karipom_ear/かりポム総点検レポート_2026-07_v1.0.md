## 観点別の所見と提言

### 1. 設計 ★★★★

**現状**：単一スーパーループ＋協調ポンプ（smartDelay等がWeb/UDP/口パクを回す）＋busyフラグ（servoBusy/soundBusy/webServoBusy）で再入を制御する設計。イベント源（タッチ・カメラ・IMU・音・ジョイスティック）はloop()でbool化されて状態機械に流れる。この構造は**一貫していて、9,000行でも破綻していない**。

**課題**：(1) ポンプの中身が場所により異なる（smartDelayは5関数、mutterSearchPumpは3関数、moveSmooth内はhandleUDPのみ）。どこで何が動き得るかが暗黙知になっている。(2) 状態機械が292個のグローバル変数に分散し、全体像がコードからしか読めない。

**提言**：①ポンプを`yieldPump()`1本に統一（引数フラグで間引き可）。②「どの状態変数を誰が書くか」の一覧表をDocsに1枚作る（コード変更不要・半日仕事・AI会話期に必ず効く）。

### 2. 保守性 ★★★（最重要課題）

**現状**：ファイル名によるバージョン管理＋日付入り変更履歴コメントは機能しているが、単一ファイル9,491行はArduino IDEでの編集・検索・差分確認の実用限界。**setup()の2,088行は59本のWebルート定義（HTML構築ラムダ）が原因**で、本来の初期化コードが埋もれている。

**提言（優先度順）**：

1. **git導入（最優先・コード変更ゼロ）**。ファイル名バージョニングは併用でよい。半年の開発で「どの変更が口パクを壊したか」を二分探索できることの価値は計り知れない。プライベートリポジトリで十分。
2. **機械的ファイル分割を「単独リリース」として1回だけ実施**（Ear Phase 1完了直後を推奨）。Arduino IDEは同一フォルダの複数.inoタブを自動結合するため、**ロジックを1行も変えずに**分割できる：`karipom.ino`（setup/loop）＋`web_routes.ino`（59ルート）＋`servo_motion.ino`＋`audio_ear.ino`＋`logging.ino`＋`config.ino` 程度の6分割。分割前後で同一動作を8時間試験して確定。以後の全開発の効率が変わる。
3. 分割時にsetup()からルート登録を`registerWebRoutes()`として抽出（呼び出し1行）。

### 3. 可読性 ★★★★

コメント率18%・全て日本語・「なぜそうしたか」（例：`getLocalTime`5秒ブロックの真犯人特定、String.removeのヒープ再配置数百ms）まで書かれており、**半年後の自分が読める**コードになっている。命名規則（handle/update/cfg_接頭辞）も一貫。改善点は長大関数の分割（保守性の項と同じ）と、ファイル冒頭の変更履歴が伸び続けている点（git導入でCHANGELOG.mdへ移せる）のみ。

### 4. 拡張性 ★★★★

刺激源追加のパターン（`updateXxxStimulus()`→loop()でbool→状態機械）が確立しており、センサー追加は低コスト。拡張性のボトルネックは2つ：(1) Web画面の追加コスト（String連結HTMLを手書き）(2) Groveポート満席（A=サーボ、B=ジョイスティック、C=Ear）。**(2)はEar v2アーキテクチャ自体が解**（後述6・8）。

### 5. PCM1808対応（Ear v2受け入れ準備）★★★★★

今回の総点検で改めて確認した結果、**受け入れ側の準備は完了している**：

- 挿入点（1458/5810/9059/1880行付近）は実在し、依存も検証済み（実装仕様書v1.2）
- FFT表示・SPEAK状態機械・途絶watchdogは既存のまま流用可能
- 唯一の残作業はPhase 1での**FFT/SPEAKパーサ共通化**（UDP/UART重複解消）。Phase 0で重複を許容する判断は妥当だが、放置すると「片方だけ直した」事故の温床になるため、Phase 1のスコープから外さないこと

### 6. 将来の人感センサー ★★★★

**結論：CoreS3ではなくPico（Ear）側に接続する。** 理由：

- CoreS3のGroveは満席。M-BUS配線はポリシー違反（分解しない）
- Ear v2プロトコルのEVENTフレーム（TYPE 0x02）に`PRESENCE_ON/OFF`を追加するだけで、**CoreS3側は配線ゼロ・受信ハンドラ追加のみ**
- センサー候補：**LD2410系ミリ波レーダー（UART、在/不在＋距離、約600円）を第一候補**、PIR（HC-SR501等、GPIO 1本、安価だが静止人体に弱い）を簡易案とする。Pico 2のGPIOは十分空いている（Phase 0終了時点で20本以上）
- 用途（睡眠/起床・接近で挨拶）は既存の`handleSleepMode`/`wakeUp()`の刺激源として自然に合流する

**注意1点**：ミリ波レーダーはサーボモーターの動きにも反応するため、首振り中は判定を無効化する（`servoBusy`参照——既存フラグがそのまま使える）。

### 7. 将来のAI会話 ★★★

**現状の素材**：Wi-Fi常時接続・Webサーバ・スピーカー（WAV再生）・独り言基盤（SD内WAVのランダム再生＋クールダウン管理）・Ear経由のVAD（Phase 2で入手）。HTTPClient/TLSの使用実績はゼロ＝完全新規領域。

**制約2つ**：

1. **内蔵マイクとスピーカーの同時使用は音割れで実質不可**（コード内に2026/06/07確認済みと明記あり）。→ AI会話の耳は**Ear（INMP441）を使う**。これはEar v2計画と完全に整合しており、追加投資不要
2. **TLS接続は瞬間40〜50KBのヒープを要求**。現状のWeb系String連結との同居が最大のリスク

**推奨の段階案**：

- 段階a（オフライン会話・Ear Phase 2直後に可能）：EarのVAD＋音種分類→「呼びかけられたら相槌WAVを返す」。クラウド不要・ヒープ影響ゼロ・体験としては会話の入口が成立する
- 段階b（クラウドAI）：発話区間のみEar→CoreS3→HTTPS でクラウドSTT/LLM/TTSへ。**着手前にTLS PoCスケッチ単体でヒープ実測**し、`largest block ≥ 60KB`を常時確保できるかを判定条件にする（ヒープ監視は既に5分毎に出ているので傾向データはすぐ集まる）
- 音声データの中継はMac経由の暫定構成（既存UDP基盤の再利用）から始めるのも現実的。CoreS3単独に固執しない

### 8. 将来の複数CPU構成 ★★★★

**Ear v2が既に第一歩**であり、方向性は正しい。半年スパンでの推奨形：

```
CoreS3（表現・UI・Wi-Fiハブ）←UART/Port C→ Pico 2（耳・DSP・センサーフロントエンド）
                                              ├─ PCM1808（有線音源）
                                              ├─ INMP441（マイク・Phase 2）
                                              └─ LD2410（人感・Phase 2以降）
```

**守るべき原則は1つ：CPU間の通信は「Earプロトコル（バージョン付きフレーム）」の1本に限定する。** センサーを増やすたびに別の通信路を生やさない（EVENTタイプを増やす）。これを守る限り、将来第3のCPU（AIゲートウェイ等）が必要になっても「CoreS3から見える相手はPort Cの向こう側1つ」のまま複雑度が増えない。逆にこれを崩すと半年で配線と依存の網になる。

### 9. メモリ管理 ★★★★

**既に実装済みの良い対策**：5分毎HEAP MONITOR（free/minFree/largest/psram）、SDログのcharリングバッファ化、webLog上限3000（String.remove頻度の意識）、addLogのsnprintf固定長化。**問題の性質を正しく理解して対処している**。

**残存リスクと提言**：

1. **Web系String連結（507か所）によるヒープ断片化**が最大の残存リスク。59ルート全部の書き換えは不要。**server.send()で最大のページ数枚だけ**をsendContent分割送信へ移す（既に33か所で実績あり＝書き方は確立済み）
2. **傾向監視をルール化**：8時間・1週間稼働でminFree/largestの推移をログから確認する習慣を（Ear Phase 0の8時間試験と同時に取れる）。「largestが起動直後比で半減したら要調査」を目安に
3. **AI会話（TLS）用にヒープ予算を先取り**：largest ≥ 60KBを守れない場合、段階bの前にWeb系のString削減を前倒しする、という判断基準をいま決めておく
4. 新規コード（Earパーサ等）は固定長バッファ方針を継続（実装仕様書v1.2で規定済み）

### 10. タスク設計 ★★★★

**RTOSタスクを使っていないのは、この規模と開発体制では正しい判断**。ESP32 ArduinoではWi-Fiスタックがcore 0、loop()がcore 1で動いており、実質2コア分業は既に得ている。タスク・キュー・排他を持ち込むと、現在busyフラグで見えている競合が不可視化され、安定性最優先の方針と矛盾する。

**提言（半年スパンで見送るべきものを含む）**：

- やる：①ポンプ統一（`yieldPump()`）②**ループ時間監視**——loop()1周の最大時間をSTATE HEARTBEATに1項目追加（数行）。「何かを追加したらループが重くなった」を数値で検出でき、半年の全開発の回帰検知器になる ③「50ms以上ブロックする処理はポンプを呼ぶ」を明文化（実質いまの慣習の文書化）
- やらない：RTOSタスクへの全面移行、割り込み駆動化、デュアルコア明示分割——いずれも得るものより失う安定性が大きい。重い並行処理はPico側（既に2コア分担設計）へ寄せるのが本システムの流儀

## 最後に

このコードベースの最大の資産は、行数でも機能数でもなく、**「不具合の原因を特定し、理由をコメントに残し、対策を仕組み化する」という開発文化がコード自体に刻まれていること**です（logtoilet、watchdog群、ヒープ監視、getLocalTime修正の経緯コメント等）。半年の開発で守るべきものはこの文化であり、本レポートの提言はすべて「その文化を、増える規模と新しい機能から守るための投資」として選定しています。大規模な書き直しは一切不要です。
